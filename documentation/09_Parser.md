# Parser Architecture

## 1. Parsing Strategy

Ferrite employs a hand-written **Recursive Descent Parser** for top-level declarations and statements, coupled with a **Pratt Parser** (Top-Down Operator Precedence) for expression evaluation.

The parser's primary responsibility is to consume the linear array of `Token`s generated by the Lexer and convert them into a hierarchical Abstract Syntax Tree (AST). It strictly enforces the syntactic rules defined in `docs/grammar.ebnf` without performing any semantic validation (e.g., it ensures `x + y` is structurally valid, but does not check if `x` and `y` are numeric types).

## 2. Why This Parser Strategy?

### 2.1 The Case Against Parser Generators (YACC/Bison)

Initially, it is tempting to use parser generators (like LALRPOP or pest in Rust) to automatically derive the parsing logic directly from the EBNF grammar. This was explicitly rejected for Ferrite.

**Drawbacks of Parser Generators:**

- **Hostile Error Messages:** When a generated parser encounters an unexpected token, it typically emits a generic "Unexpected Token X" error and aborts compilation.
- **Inflexible Recovery:** It is notoriously difficult to instruct a generated parser to skip malformed code and resume parsing at the next valid statement.
- **Debugging Complexity:** Tracing a bug in the generated state machine of an LALR(1) parser is far more difficult than stepping through a standard Rust function call stack.

### 2.2 The Case for Recursive Descent

By writing the parser by hand:

- We achieve absolute control over error diagnostics.
- We can construct custom, context-aware error messages (e.g., "Expected `{` to begin the `train` block, found `)` instead.").
- We can easily embed synchronization logic to support **Panic-Mode Error Recovery**.

## 3. AST Generation

The parser maps non-terminals in the grammar directly to Rust structs and enums located in `src/ast/mod.rs`.

- **Nodes:** Every syntactical construct is an AST node (e.g., `IfStmt`, `GroupDecl`, `BinaryExpr`).
- **Memory Management:** Because AST nodes are recursively defined (an `IfStmt` contains a `Block` which contains another `IfStmt`), the parser heavily utilizes heap allocation (`Box<Expr>`, `Box<Stmt>`).
- **Metadata Retention:** The parser attaches the original Lexer `Span` to every AST node. This is critical for the Semantic Analyzer and Code Generator to emit accurate error pointers later in the pipeline.

## 4. Parser Algorithms

### 4.1 Recursive Descent (Statements & Declarations)

For statements and declarations, the parser looks at the current token (`peek`) and routes execution to the appropriate parsing function.

- If it sees `fun`, it calls `parse_function_declaration()`.
- If it sees `if`, it calls `parse_if_statement()`.
  This maps the parsing logic directly to the call stack.

### 4.2 Pratt Parsing (Expressions)

For binary and unary expressions, standard recursive descent leads to massive call-stack overhead (e.g., `parse_addition` calls `parse_multiplication` calls `parse_unary`).

Ferrite uses a **Pratt Parser** algorithm for expressions. Pratt parsing assigns a binding power (precedence level) to every operator. The parser loops, consuming operators as long as their binding power is higher than the current context. This elegantly handles operator precedence (e.g., `*` binds tighter than `+`) and associativity entirely in a tight, fast loop rather than relying on deep recursion.

## 5. Error Recovery (Panic-Mode)

When the parser encounters a syntactic violation, it does **not** halt compilation or panic the Rust thread.

**The Panic-Mode Algorithm:**

1. **Detect:** An unexpected token is found (e.g., missing `;`).
2. **Report:** The parser formats a highly descriptive error string, attaches the token's `Span`, and pushes it into the global `DiagnosticBag`.
3. **Synchronize:** The parser enters "panic mode". It discards tokens sequentially until it finds a reliable synchronization boundary. In Ferrite, synchronization boundaries are typically statement terminators (`;`), block closures (`}`), or the start of a new declaration (`fun`, `group`, `keep`).
4. **Resume:** Once synchronized, panic mode ends, and the parser resumes normal execution.

**Engineering Benefit:** This allows the compiler to detect and report 15 syntax errors in a single run, rather than forcing the developer to recompile 15 times to find them one by one.

## 6. Future Improvements

- **Arena Allocation:** Currently, the parser relies heavily on `Box<T>` for AST nodes. This spreads the AST randomly across the heap, leading to cache misses during semantic analysis. Future versions should migrate to an Arena Allocator (e.g., `bumpalo`), allocating all AST nodes contiguously in memory for extreme cache locality.
- **Incremental Parsing:** For the IDE Language Server (LSP), the parser should eventually support incremental parsing—only re-parsing the specific function or block that the user is currently editing, rather than the entire file.
