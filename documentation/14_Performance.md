# Performance Architecture

## 1. Overview

Ferrite aims to provide near-instantaneous compilation times, maintaining sub-10ms feedback loops for Language Servers (LSP) while scaling to codebases exceeding hundreds of thousands of lines of code. This document outlines the time and space complexities of the compiler's internal passes, identifies current architectural bottlenecks, and tracks upcoming optimizations.

_(Note: This document describes the performance of the **compiler**. The performance of generated LLVM native binaries is heavily dependent on LLVM optimization passes `-O3` and target hardware vectorization capabilities.)_

## 2. Time Complexity

The compiler operates as a strictly linear pipeline. Its overall theoretical time complexity is $O(N + V \log V)$, where $N$ is the size of the source code and $V$ is the number of declared variables/symbols.

### 2.1 Lexical Analysis (O(N))

The Lexer processes the source `&str` using a single-pass `peek()` and `next()` iteration strategy.

- **Time Complexity:** $O(N)$, where $N$ is the total number of bytes in the file.
- **Characteristics:** Highly cache-friendly. The CPU strictly pre-fetches the contiguous byte array. No regex engines or backtracking state machines are used.

### 2.2 Parsing (O(T))

The Recursive Descent Parser processes the array of Tokens generated by the Lexer.

- **Time Complexity:** $O(T)$, where $T$ is the number of tokens. In the absolute worst-case scenario involving deeply nested parentheses `(((((x))))`, the call stack overhead scales linearly, but Pratt Parsing keeps expression evaluation extremely flat.

### 2.3 Import Resolution (O(F + E))

The Import Resolver builds the module dependency DAG.

- **Time Complexity:** $O(F + E)$, where $F$ is the number of files and $E$ is the number of `import` edges between them. Cycle detection employs a standard Depth-First Search (DFS) topological sort, ensuring cyclical imports are caught instantly.

### 2.4 Semantic Analysis (O(V))

The Semantic Analyzer walks the AST twice (Pass 1 and Pass 2).

- **Time Complexity:** Average $O(V)$ where $V$ is the number of AST nodes.
- **Type Lookup:** Variable lookups in the `TypeEnv` rely on Rust's `HashMap<String, Type>`. Hash map insertions and lookups are amortized $O(1)$, but string hashing incurs a slight overhead relative to string length.
- **Unification:** Unifying complex types (e.g., deeply nested generic tensors) takes $O(D)$ where $D$ is the nesting depth of the generic parameters.

## 3. Space Complexity

### 3.1 Lexer Space (O(T))

The Lexer currently allocates a `Token` vector proportional to the source size. Identifiers and Strings are cloned into heap-allocated `String` structs, leading to $O(T)$ heap allocations.

### 3.2 AST Memory Model (O(V))

The Parser allocates every AST node onto the heap using `Box<T>`.

- **Space Complexity:** $O(V)$.
- **Overhead:** A 64-bit pointer is required for every edge in the AST, leading to significant memory fragmentation.

## 4. Current Bottlenecks

### 4.1 String Allocation and Hashing

The single largest performance bottleneck in the compiler front-end is `String` allocation.

- Every identifier parsed creates a new heap-allocated `String`.
- The Semantic Analyzer uses these `String`s as keys in the `TypeEnv` `HashMap`.
- Rust's default `SipHash` algorithm is cryptographically resistant to hash-collision DOS attacks, but it is comparatively slow for the short, predictable identifiers commonly used in programming languages (e.g., `x`, `idx`, `tensor`).

### 4.2 AST Heap Fragmentation

Because the parser uses `Box<Expr>` and `Box<Stmt>`, nodes are scattered arbitrarily across the heap by the OS allocator. When the Semantic Analyzer traverses the AST, it suffers from frequent CPU cache misses.

## 5. Optimization Opportunities

To achieve the ultimate goal of parsing and type-checking 1,000,000 lines of code per second, the following architectural upgrades are mandated for future versions:

### 5.1 String Interning

All `String` identifiers generated by the Lexer must be replaced with a `Symbol` (a 32-bit `u32` integer pointing to a global string interning pool).

- **Benefit:** Reduces `Token` size. Replaces costly string hashing in the `TypeEnv` with ultra-fast integer hashing.

### 5.2 Fast Hashing (FxHash / AHash)

Replace Rust's default `SipHash` in the `TypeEnv` with `rustc-hash` (FxHash) or `ahash`.

- **Benefit:** These algorithms drop cryptographic guarantees in exchange for raw hashing throughput, significantly speeding up semantic variable lookups.

### 5.3 Arena Allocation (Bumpalo)

Remove `Box<T>` from the AST. Instead, the Parser should take a reference to a `bumpalo::Bump` arena and allocate all AST nodes contiguously.

- **Benefit:** Near-zero allocation cost (simply advancing a pointer). Perfect CPU cache locality during Semantic Analysis. Zero deallocation cost (the entire arena is dropped at once at the end of compilation, bypassing recursive tree drops).

### 5.4 LLVM Metadata Elision

When targeting the LLVM codegen, heavily generic code can result in massive LLVM IR files due to monomorphization. Future codegen optimizations must aggressively deduplicate monomorphized functions if their resulting LLVM IR signatures match identically (e.g., generic functions that have the exact same machine code representation despite differing type names).
